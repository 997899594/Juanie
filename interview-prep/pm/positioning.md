# PM 路线：产品定位

## 30 秒版本

Juanie 定位为 AI 原生发布控制平面。它服务的不是“把代码跑起来”这个单点，而是“从创建项目到安全上线”的完整决策链：
环境、数据库、预览、发布、验证、放量、失败诊断和 AI 辅助。

## 用户是谁

核心用户不是单一角色，而是一组围绕发布协作的人：

| 用户 | 他们在乎什么 |
| --- | --- |
| 创始团队 / 小团队技术负责人 | 快速上线，少踩部署和数据库坑 |
| 产品工程师 | 分支有变更后马上生成可看的 preview |
| 后端工程师 | 数据库迁移安全、环境变量准确、发布失败可排障 |
| DevOps / 平台工程师 | 环境治理、权限、审计、标准化发布 |
| PM / QA | 能看到需求级 preview 和发布状态，不用追着工程师问 |

## 市场位置

Juanie 不应该被讲成单纯替代 Vercel、Railway、Render、Argo CD 或 GitHub Actions。

更准确的位置是：

- 它像 PaaS 一样提供环境和部署体验。
- 像 DevOps 控制面一样管理 release、rollout 和环境策略。
- 像数据库平台一样关注 schema safety。
- 像 AI 工具一样压缩排障和判断成本。

所以一句话可以是：

> Juanie 是面向 AI 时代应用团队的 release control plane，重点解决应用上线过程中的环境、数据库、
> 预览、放量和智能诊断闭环。

## 为什么现在需要

现代团队的软件交付变复杂了：

- 一个需求通常对应一个分支、一个 MR/PR、一个 preview。
- 数据库变更越来越频繁，ORM 和 migration 经常不同步。
- 小团队没有完整平台组，但也需要生产级发布安全。
- AI 提高了写代码速度，也放大了“代码更多但发布风险更高”的问题。
- 传统 CI/CD 更多关注执行，不关注“是否应该继续发布”的决策。

Juanie 的机会就是把发布从脚本流水线提升成平台化、智能化、可审计的决策过程。

## 产品差异化

| 差异点 | 解释 |
| --- | --- |
| Release-first | 以 release 状态机组织用户心智，而不是一堆资源页 |
| Schema-aware | 数据库变更是发布门禁的一等公民 |
| Preview-native | preview 是需求验证环境，不是 staging 的临时副本 |
| AI-native | AI 基于平台证据解释风险和下一步，不是外置聊天 |
| Governed | 团队 binding、RBAC、Secret/TLS、审计和 trace 是主链路能力 |
| Pragmatic | 平台自身 GitOps，子应用发布不强制 GitOps，避免脏历史和重复路径 |

## 面试可讲的产品原则

1. 不把所有技术能力都暴露给用户，用户只需要知道下一步。
2. 不为了“现代化”引入伪命题，比如子应用每次发布都写 GitOps 历史。
3. 不让 AI 抢主流程，AI 要服务发布判断。
4. 不把 preview、staging、production 混成一种环境。
5. 不追求全自动到失控，生产写操作要有确认、审计和可回滚。
